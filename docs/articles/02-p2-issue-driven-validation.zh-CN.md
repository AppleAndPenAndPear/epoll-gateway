# P2：在基线已验证后，用 issue 与公开讨论来做下一步验证

> 这是一篇项目规划草稿，不是功能宣称。当前假设是：在发布包和本地正确性基线都已经稳定之后，项目不应该继续把“访谈”作为唯一的下一步信号，而应该转向“相关 issue 分析 + 公开技术讨论 + 文章输出”的方式来推进 P2。这样能在不拖住工程工作的情况下，收集外部反馈。

## 为什么 P2 适合这样做

当前项目的基线已经比最初阶段清晰很多：

- 发行包和跨发行版验证已稳定
- CI 和集成断言已通过
- benchmark 路径已修正且结果已记录
- 当前已知的主要限制也已经明确，例如异步上游 fan-out 和 API composition 的边界问题

这说明项目已不处于“只会跑通一个 demo”的探索阶段，而是进入了下一层“选择正确工程取舍”的阶段。

因此，P2 的问题不再是“能不能做出一个可运行网关”，而是：

- 我们构造异步上游模型时，应该如何控制并发、超时和退避？
- 上游慢节点和上游失败如何在不阻塞事件循环的前提下做到可控？
- 什么时候才应该进入 API composition，而不是把它做成过早的产品承诺？

这类问题，最好的下一步信号并不是简单地“找用户聊”，而是结合相关开源项目里的 issue 与实践讨论来校准。

## P2 的工作方式

### 1. 保持工程目标足够窄

P2 应聚焦在“有边界的异步上游基础设施”：

- 不能让 epoll worker 在等待上游时被阻塞
- 明确 queue / concurrency / memory 边界
- 明确 deadline 和 cancellation 语义
- 处理 overload 和 shutdown 行为
- 对慢后端、失败后端和断连后端做稳定测试

P2 的关键产出是行为模型，而不是广泛功能承诺。

### 2. 选一小批相关 issue 作为外部信号源

重点不是做大规模市场研究，而是挑 2-3 个和同类问题密切相关的外部 issue：

- 上游慢请求与超时行为
- 并发队列与 backpressure
- API composition 下的部分失败语义
- graceful shutdown 期间请求被打断的场景
- 异步调用模式下的资源限制

从中收集的问题可以包括：

- 实际用户常见的失败模式是什么？
- 默认超时和重试策略如何被接受？
- 组合场景里“部分成功 / 部分失败”是否被视为需要设计保证？
- 在不引入复杂控制面的前提下，哪类职责最值得做成稳定能力？

### 3. 把讨论整理成一篇公开文章

产出应该是一篇简短技术文章或说明文，而不是“完结式产品文案”。文章内容应覆盖：

- 当前已验证的基线是什么
- 当前明确不做什么
- P2 设计的边界和权衡
- 外部 issue 讨论给到的主要启发
- 为什么异步上游不是“全面编排平台”，而是有边界的基础设施

这篇文章的目的不是“说服所有人”，而是让评论者给出真实反馈，并为之后的更正式访谈打底。

## 为什么不直接做访谈

访谈是有价值的，但在当前阶段，它容易带来大量未排序需求。这对一个仍在补基础的项目并不一定是最有效的信号。

相比之下，issue-driven discussion 的优势更明显：

- 反馈直接来自真实故障与工程权衡
- 不会因为“调研对象很多”而拖住核心开发
- 能更快让项目知道哪些能力应该做得更严谨
- 为后面的正式访谈和更大规模发布准备文章与材料

## 具体下一步

1. 完成 P2 的异步上游基础设计和边界测试。
2. 选一小批相关开源项目中的 issue 作为对照研究对象。
3. 把设计取舍和外部讨论整理为一篇公开文章。
4. 在社区渠道中发布，并收集评论反馈。
5. 只有在基础能力更成熟之后，再回到更正式的用户访谈阶段。

这样做的核心原则是：在工程基线已经穩定之后，继续推进产品判断，但不让“访谈门槛”拖住 P2 的节奏。它兼顾了工程推进、外部验证和公开讨论的可信度。
