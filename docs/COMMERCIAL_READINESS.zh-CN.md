# 商用就绪与 AI 网关演进清单

本文是项目后续能力的登记表，不表示所有能力都必须实现。状态以当前代码和测试为准；优先级应结合访谈、试用和付费意向调整。总体原则是先把单机部署、配置驱动、可审计的 API 网关做可靠，再用可选能力承接 AI 流量，不为追赶概念而重写产品定位。

状态说明：**已有** 表示当前已实现；**部分** 表示有基础但离生产需求仍有缺口；**待做** 表示尚未实现；**按客户决定** 表示只有目标客户明确需要时才投入。

## 产品判断：API 网关还有没有未来

API 网关没有因为大模型而失去价值。AI 应用本身仍通过 HTTP API 访问模型、检索、身份、计费和业务服务；入口鉴权、路由、限流、TLS、审计、运维和流量治理仍然需要。变化在于，单纯“按路径转发 HTTP”的网关差异化变弱了，AI 流量又引入模型选择、令牌/成本配额、流式响应和模型级可观测性等新问题。

因此建议**保留 API 网关作为稳定内核，把 AI 网关能力做成可选的上层路由与策略**，而不是现在全面转向 AI 专用产品。这样既能服务普通 API/边缘/OEM 场景，也能逐步验证 AI 用户是否愿意为模型路由、预算治理和审计付费。只有在用户访谈、真实部署或付费意向证明 AI 场景是主要市场后，才考虑把 AI 网关提升为主定位。

不建议近期承诺“全能 AI 安全平台”、语义缓存、提示词防火墙或模型市场；这些能力复杂、供应商变化快，且需要数据治理与评测体系支撑。优先做协议正确、成本可控、可观测、可回退的模型 API 流量管理。

## 能力登记表

### P0：让现有数据面能安全承接真实业务

| 能力 | 当前状态 | 后续目标与完成标准 |
|---|---|---|
| 多后端 API 聚合 / BFF | **待做**。一条 route 只引用一个 upstream；目前不是多服务编排器。 | 提供受限的 composite route：多个命名调用、并行执行、输入/输出映射、必需/可选依赖、明确的部分失败语义。以用户资料、订单、推荐、未读消息、优惠券的端到端示例验证。 |
| 聚合可靠性与资源边界 | **待做**。upstream 转发当前同步执行。 | 聚合调用必须有总 deadline、每依赖超时、并发/队列上限、取消与失败隔离；不能在 epoll worker 中同步串行等待。只有经过压力测试证明有界，才算完成。 |
| 聚合诊断与控制 | **待做**。现有 trace ID 主要覆盖单个入站请求。 | 子调用传播 trace context，记录依赖名、耗时、状态、重试和错误类型；限制敏感请求/响应日志；支持失败降级和可追踪的部分响应。 |
| 身份认证扩展 | **部分**。当前 API Key、route allow/deny、Host/Tenant 绑定已实现。 | 按目标客户补 JWT/OIDC/JWKS、角色/权限映射和密钥轮换；完成前不得宣称支持企业 SSO。先确认用户确实需要，不把所有身份协议一次性做进核心。 |
| 请求与响应策略 | **部分**。有路由和代理，但没有通用的映射/转换策略层。 | 明确支持范围后再加 Header/路径/查询参数映射、CORS、请求体大小限制和脱敏。转换必须可验证、可测试，避免任意脚本造成不可控执行。 |
| 上游流量管理 | **部分**。已有 round-robin、TCP 健康检查、连接池、重试和基础熔断。 | 按需增加权重/金丝雀发布、基于比例的故障切换及可解释的健康状态；重试预算受总 deadline 限制，并保持非幂等请求不自动重发。 |
| 上游 TLS 身份 | **部分**。HTTPS 上游校验已实现；mTLS 尚未实现。 | 当客户有服务身份要求时支持客户端证书、证书热轮换和 mTLS 集成测试；默认拒绝跳过证书校验。 |
| HTTP 协议边界 | **部分**。当前主要是 HTTP/1.1；不应暗示支持 HTTP/2、gRPC 或 WebSocket。 | 访谈确认协议需求后，选择性实现/接入 HTTP/2、gRPC 或 WebSocket，并通过兼容性、背压、超时、连接复用和长连接压测。明确不支持的协议也要写入文档。 |

### P1：商用部署与运营闭环

| 能力 | 当前状态 | 后续目标与完成标准 |
|---|---|---|
| 多实例与高可用 | **部分**。单实例有健康检查和优雅停机；实例间不共享状态。 | 明确单机/边缘产品边界；若需要集群，定义限流配额、熔断、配置和密钥在多实例下的一致性语义，以及滚动升级/回滚方案。不要先引入重型控制面。 |
| 分布式限流与配额 | **部分**。单进程跨 worker 共享，多个进程/主机不共享。 | 客户需要全局配额时，设计可选共享存储或明确采用近似配额；规定存储故障时 fail-open/fail-closed 策略，并测试超卖范围。 |
| 配置变更治理 | **部分**。热加载会校验并保留旧配置，但 worker 不是同一时刻切换；配置来自文件。 | 暴露配置版本/摘要、变更来源与应用状态，提供可审计回滚；明确 reload 的原子性边界。Admin API 继续与公网数据面隔离，并补管理流量 TLS/访问控制部署指引。 |
| 运营指标和追踪 | **部分**。已有 Prometheus 全局指标、X-Trace-Id 和日志；维度直方图及 OpenTelemetry 未完成。 | 补 route/upstream 延迟与失败率、限流/熔断/重试/连接池指标、traceparent/W3C context；控制标签基数并避免密钥、个人数据进入指标或日志。 |
| 日志与审计管理 | **部分**。已有 CLF/AUDIT，但每请求日志开关在路线图中仍待做；外部审计存储未集成。 | 可分别控制访问日志与安全审计；安全审计不可被普通访问日志开关关闭。定义日志轮转、字段脱敏、保留期限和外送方式。 |
| 容量与性能证明 | **部分**。有基准报告，但目前已知同条件测试中吞吐低于 Nginx，聚合尚无基准。 | 按代表性场景持续报告 P50/P95/P99、吞吐、错误率、CPU/RSS、连接数；覆盖 TLS、远端上游、慢后端、混合流量及聚合扇出，并保留复现脚本和机器条件。 |
| 运行时限额与抗压 | **待做/需核实**。现有连接、请求体、队列等资源预算需要形成统一的部署容量说明。 | 建立最大连接、请求/响应体、上游并发、文件描述符、内存及过载行为预算；过载时明确拒绝/排队策略，避免无界增长。 |
| 安全供应链 | **部分**。已有协议/TLS加固、配置校验和 ASAN 支持。 | 增加依赖与发行物安全扫描、SBOM/校验和、模糊测试、定期安全回归；建立漏洞响应和受支持版本策略。若目标行业要求合规认证，先由客户需求驱动。 |
| 安装、升级与支持 | **部分**。有发行包、Docker、systemd 和升级文档。 | 明确支持平台/依赖/升级兼容矩阵、配置迁移策略、版本生命周期和故障收集方式；验证升级失败回滚和备份恢复。 |

### P2：按市场信号选择的 API 网关能力

- **API 生命周期**：API 版本治理、弃用通知、OpenAPI 校验/导出、兼容性测试。当前未见完整生命周期管理；做多大取决于是否面向 API 发布团队。
- **流量策略扩展**：一致性哈希、会话粘性、地域/权重路由、熔断窗口和失败率阈值。当前以 round-robin 和基础熔断为主；先用具体场景证明收益。
- **缓存与幂等保护**：可配置响应缓存、缓存键/失效规则、幂等键保护。当前缓存主要面向静态文件；业务响应缓存需谨慎处理身份和租户隔离。
- **企业身份与授权**：OIDC/OAuth2 集成、JWT claims 映射、细粒度 RBAC、审计导出。属于客户驱动项，不应仅为功能清单引入身份提供方依赖。
- **集群控制面/服务发现**：多节点配置分发、注册发现、配额统一与状态同步。当前定位强调单二进制和无外部依赖；除非客户愿意承担复杂度，不应默认引入 etcd/Kubernetes 依赖。
- **生态和集成**：日志/指标/告警接入、常见密钥管理系统、部署模板。优先稳定协议和文档化集成点，不急于建设插件市场或大型控制台。

| 能力 | 当前状态 | AI 场景的完成标准 |
|---|---|---|
| 模型供应商适配与路由 | **待做**。现有 upstream 是通用 HTTP 服务组，不理解模型/供应商语义。 | 先支持少量有真实用户需求的兼容 API；定义模型名到供应商/模型的映射、路由规则、超时和可回退条件，保留原始 API 兼容性边界。 |
| Token / 成本配额 | **待做**。当前令牌桶按请求限流，不按模型 token 或费用计量。 | 支持按租户/密钥/模型维度设置请求与 token 预算；成本估算、账期和计数准确性须标明，不把估算值冒充账单级计量。 |
| 流式响应 | **待做/需验证**。现有代理读取完整后端响应后再构造响应，不能据此宣称支持低延迟 SSE 流式转发。 | 正确转发 SSE/chunked 流，端到端背压、客户端断连取消、空闲超时、首 token/总耗时指标齐全；内存随连接数有界。 |
| 模型级可靠性 | **部分**。有通用重试和熔断基础，但缺少模型语义。 | 仅对可安全重试的请求/错误重试；按模型和供应商隔离熔断，配置 fallback，并限制整体 deadline 与重复计费风险。 |
| AI 使用观测 | **待做**。现有指标不含模型、token、首 token 延迟或成本。 | 记录模型、供应商、token 用量（若响应提供）、首 token/总耗时、错误和估算费用；默认不记录提示词/响应正文，支持脱敏和租户隔离。 |
| 凭据与审计 | **部分**。API Key 可外置，但缺少多模型供应商凭据治理。 | 供应商密钥外置、最小权限、轮换和审计；不得在日志、错误响应、指标标签或管理 API 中泄露凭据。 |
| 提示词安全、内容审核、语义缓存、工具/MCP 网关 | **待做，暂不承诺**。 | 只有在明确客户、威胁模型、评测集、数据处理边界及维护成本后再立项；优先以可插拔外部策略集成，不把模型安全效果作绝对保证。 |

## 建议实施顺序与验收门槛

1. **先收敛事实与基线**：修正项目状态文档中过期条目；明确支持协议、单实例边界、当前指标和已知性能差距。以 CI、集成测试和基准可复现作为后续改动门槛。
2. **API 聚合 MVP**：先完成有界并行调用、deadline、取消、部分失败语义和子调用追踪；用真实组合页面案例验证，保留现有单 upstream 路径不变。
3. **数据面安全/可靠性**：根据访谈决定 OIDC/JWT、mTLS、流量权重、请求大小与资源预算。每项都需配置校验、失败模式定义和集成测试。
4. **运营闭环**：访问日志开关、低基数的 route/upstream 指标、traceparent、配置变更审计/回滚、负载与故障注入测试。
5. **AI 网关试点**：先访谈并取得至少一个真实试用场景，再选模型路由、token 配额、SSE 流式转发、成本/延迟观测中的最小组合。设定用户采用/付费信号；没有信号就继续完善通用 API/边缘网关，不扩张 AI 功能面。
6. **集群与企业能力**：只有多个真实用户明确需要时，再决定分布式配额、控制面、SSO、合规认证及商业授权方案。

每个能力落地时更新本表状态、`PROJECT_STATUS.md`、测试数量和 `CHANGELOG.md`；不以“代码已合并”作为完成标准，而以配置校验、故障场景测试、可观测性和用户文档齐备作为 DoD。
